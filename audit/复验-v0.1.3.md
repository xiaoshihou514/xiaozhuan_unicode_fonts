## 二、未闭环项

### 2.1【阻断级·未闭环】常用简体字仍借成别的字的篆形（字体与琅琊两端都有）

**现象**（v0.1.3 陈昌治本，其余三款相同；`langya.map` 的篆形列与楷化列也一样）：

| 输入 | 显示（借了谁） | 应有 | 查表链命中路径（`zhuan -d`） |
|---|---|---|---|
| 亲 | 榛 | 親 U+3E8DB | 变体链 亲→榛（语义借形） |
| 园 | 刓 | 園 U+3E1D9 | 变体链 园→刓（语义借形） |
| 历 | 厲 | 歷 U+3D4B1 或 曆 U+3E34F | 变体链 历→厲（语义借形） |
| 柳 | 檉 | 柳（《說文》作「桺」） | 变体链 柳→檉（语义借形） |
| 愈 | 愉 | 瘉 或 未收 | 变体链 愈→愉 |
| 磁 | 瓷 | 未收 | 变体链 磁→瓷 |
| 肆 | 四 | 肆字头 | 变体链 肆→四 |
| 吨 | 啍 | 未收 | 变体链 吨→啍→說文對位 |
| 氯 | 綠 | 未收 | 变体链 氯→綠 |
| 谭 | 談 | 譚 或 未收 | 变体链 谭→譚→談 |

证据：[残余错映-v013.png](证据/复验/残余错映-v013.png)。第一行与第二行同形，说明这些字借了别字的字形；第三行是亲、园、历应有的繁体本字字形。

**范围**：`langya.map` 中走「语义借形」路径的共 1,201 条，其中 GB2312 一级字 308 条（清单见 `数据/复验/语义借形清单.tsv`）。大部分是正常的简→繁转换（万→萬、东→東），以上 10 条是人工逐条看出的明显错误。首轮精筛只覆盖了「本身就是《說文》字头」的字，这一类简体字不在 107 条之内，是**同一根因的漏网部分**。

**附带问题**：琅琊对「亲」打了补丁，`export_char_map.py:51-57` 的 `overrides_pre` 只改写了篆形列，**楷化列仍是「榛」**，所以楷化模式输入「亲」上屏「榛」（探针场景 16 实测）。字体侧 `modern_map.tsv` 里「亲」仍映射到 U+3DFE5（榛），两端不一致。

**建议**：① 对简体字，查表链应先走简→繁（OpenCC 或 Unihan kTraditionalVariant）找到繁体本字，再查本字，最后才考虑语义变体；② 逐条复核这 308 条，结论写进白名单或裁定表；③ 两端黄金表都补上上面 10 个字，楷化列一并断言；④ 覆盖机制要同时改写楷化列。

### 2.2【轻微·未闭环，兼新缺陷】碎屑过滤条件写反了

- **代码**：`build_ttf_from_paths.py`（`build_family`）中 `kept = [c for c in contours if abs(contour_area(c)) >= DEBRIS_AREA or contour_area(c) < 0]`，意思是「面积为负的轮廓无论多小都保留」。
- **事实**：源路径翻转 y 轴后，**外轮廓的有向面积为负**（四款 43,804 个字形逐一核对：最大轮廓全部为负），孔洞为正。所以这条规则保留了全部黑色碎屑（外轮廓），删掉的是面积小于阈值的**孔洞**。
- **实测**：按构建口径重算，被删的小孔洞在陈昌治本有 2,807 个（涉及 2,261 个字形），徐锴本 572/458，段玉裁本 888/630，藤花树本 32/30，合计约 3,380 个字形；段玉裁本保留下来的小碎屑有 1,416 个。三版对照（[小镂空被填抽样.png](证据/复验/小镂空被填抽样.png)）显示，被填掉的主要是码表扫描造成的笔画内白点。这在视觉上**近乎有益**，但删除时不区分大小以外的任何特征，和设计镂空之间没有界线；同时它声称要解决的 G6（黑色碎屑）完全没有解决（[碎屑残留抽样.png](证据/复验/碎屑残留抽样.png)）。
- **建议**：按「与最大轮廓同向（外轮廓）且面积小于阈值」来判定碎屑，与审计口径一致。白点是否填掉单独决定，并明确写进文档。修好后用首轮的 33 条清单回归。

## 三、新发现

### 3.1 琅琊 B2 修复仍有遮蔽漏洞（严重度：中）

`xmake.lua` 的 on_install 用 `os.isfile(path.join(sysprefix, "lib64", "fcitx5"))` 判断系统模块**目录**。xmake 中 `os.isfile` 对目录返回 false（实测：`xmake l os.isfile /usr/lib64/fcitx5` 得 false，`os.isdir` 得 true），所以 `syslibaddon` 永远为空。后果是「系统已提供 libchttrans/libpunctuation 就跳过复制」这条判断永远不成立，模块 .so 仍会复制进 `~/.local/lib/fcitx5`，而 `FCITX_ADDON_DIRS` 又把它排在系统目录之前，**遮蔽依旧**。addon conf 的判断用的是 `sysshare`（文件判断正确），会跳过 conf，但 .so 已经先复制过去了。改成 `os.isdir` 即可。

另外两点：libIME 只按 `lib64/libIMECore.so.0` 探测，Debian 系（`lib/x86_64-linux-gnu`）会误判为「系统没有」而复制；本机当前的 `~/.local` 安装还是 **10-25 的旧版**（`langya.so` 修改时间为 10-25，`environment.d` 也是旧格式），本轮所有修复**都没有部署到主人的桌面**。

### 3.2 v0.1.3 撤销映射时误伤了同字异体（轻微）

相对 v0.1.1，陈昌治本 cmap 少了 53 条（清单见 `数据/复验/v013移除映射.tsv`）。除了「滚」等确实错误的漂移之外，还有一批**是同一个字的不同写法**，被一并撤掉了：弑→弒、隠→隱、軆→體、槪→槩、尅→克、凴→凭、噑→嗥、墰/壜→壇、啣→銜、㕑→廚、鵞→䳘，以及古今字 襟→紟（衿）、桌→櫂（棹）、樽→罇。建议把 Unihan kSemanticVariant 中同时也是 kZVariant 或字形变体的边（即确属同字的）保留为终端命中，只撤真正的「语义借用」。

### 3.3 head.fontRevision 写错（轻微）

`build_ttf_from_paths.py` 中 `fontRevision = (major << 16) + (minor << 4)`，结果是整数 16，fontTools 按定点数 16.0 写入。v0.1.3 四款实测都是 16.000，name ID 5 却是「Version 0.1.3」，两者不一致。建议直接写浮点数，例如 `float(f"{major}.{minor:01d}{patch:02d}")`，或者至少保证 head 与 name 一致。

### 3.4 竖排 tsb 为常数且没有 VORG（建议）

vmtx 中所有字形的 tsb 都是常数 41，又没有 VORG 表。HarfBuzz 对 CFF 字体用 ascender 作竖排原点，实测显示正常（[竖排-一二田-v013.png](证据/复验/竖排-一二田-v013.png)）。但用「yMax + tsb」推原点的渲染器（部分 DirectWrite、CoreText 路径）会让扁字贴着格子顶部。建议改成逐字 `tsb = ascender − yMax`，或者补一个 VORG（默认值等于 ascender）。

### 3.5 其他

- `core/CMakeLists.txt` 把 chttrans.conf 安装到**绝对路径** `/etc/xdg/fcitx5/conf`：非 root、自定义前缀（如 `~/.local`）的 `cmake --install` 会在这一步失败。建议改用 `${CMAKE_INSTALL_FULL_SYSCONFDIR}/xdg/fcitx5/conf`。Android APK 中仍带着 `assets/etc/xdg/fcitx5/conf/chttrans.conf`（宿主不设 `XDG_CONFIG_DIRS`，读不到），与注释所说的「不随 config 组件打包」不符。
- 首轮琅琊报告中仍未处理的轻微项：L1（组字中回车上屏候选，而不是原始字母）、L3（小键盘小数点被转成「。」）、L6（词典加载不捕获异常）、L7（语言模型缺失检测与解析器路径不一致；本次测试环境实测，LIBIME_MODEL_DIRS 下明明有模型，却报「未找到 zh_CN.lm」）、L8（punctuation 仍是硬依赖）、L9（成员声明顺序）、L12（文档仍写「候选窗口提示說文未收」，代码没有实现），以及数据管线中 luna 缓存缺失时静默缩小字符集。

**更正首轮附录甲**：首轮探针 probe3 中 Q1–Q5 场景是用 `s(a)+s(b)+…` 拼接发送按键的。C++ 不规定重载 `operator+` 两个操作数的求值顺序，GCC 实际是从右往左发送的。因此首轮 Q1「上屏 in」是**探针自身造成的假象**。首轮 K4 的结论（窗口打开时字母被吞、Esc 和退格漏给应用、失焦后窗口残留）另有按顺序发送的 P5、P6、P6b 和 probe4 独立印证，结论不变；本轮探针已全部改成逐键顺序发送。
